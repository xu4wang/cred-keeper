工作原理

一次刷新经历了什么，以及 cred-keeper 如何保证不丢唯一的 refresh token。

权威副本（vault）与发布文件

每个账号在 <dataDir>/vault/<id>.json（0600）保存一份权威副本；credentialPath 只是发布给使用方读的那一份。两者每分钟比对一次：

  • 发布的文件被清空、损坏、处于登出状态，或者比副本旧 → 从副本重新发布（损坏的文件另存为 vault/<id>.quarantine-*.json）。
  • 发布的文件比副本新（例如有人重新登录了）→ 收编为新的副本（被替换的副本另存为 vault/<id>.displaced-*.json）。

一个凭证文件只能属于一个账号：两个账号配置同一个 credentialPath 会被直接拒绝。

刷新

AT 剩余时间不超过 marginMin 分钟（默认 120，另加 0–5 分钟随机抖动）时刷新。收到 HTTP 200 后，先把原始响应文本原样保存到 <dataDir>/pending/，再解析、更新副本、更新发布文件，最后执行 onRefreshed。

  • pending 写不进去时改写另一个目录里的应急位置；应急位置也失败就留在内存里，每个周期重试写入。新凭证本身照常应用。
  • 副本写不进去时，新凭证留在内存里，每分钟重试写入。

刷新结果

结果处理
网络失败重试；连续第 2 次失败（或 AT 已低于 redMin）时告警 refresh_failed
invalid_grant进入 dead，需要人工重新登录；绝不会用同一个 RT 重试
格式不对的 400告警（很可能是接口契约变了）
200 但字段不认识进入 critical，保留 pending 响应，等人处理

pending 响应绝不静默丢弃

服务启动时和每个周期都会检查 pending 响应：

  • 它是基于当前副本发出的 → 应用。
  • 副本里已经带有它的 AT 或 RT（之前应用过）→ 删除。
  • 否则保留，账号进入 critical，同一份 pending 只报告一次。pending 未解决期间不会发起新的刷新：它可能持有唯一有效的 RT。

人工处理：cred-keeper pending <id> apply|discard --confirm <id>。响应不是基于当前副本时，apply 还必须加 --replace <当前副本指纹>。

锁

每个账号一把锁，只在该账号刷新、恢复、对账、补写期间持有。锁里记录持有者 pid 和进程启动时间，持有者崩溃或 pid 被复用都能识别为陈旧锁。status() 只读，不拿锁。

用量

每 usagePollMin 分钟（默认 10）调用一次 GET /api/oauth/usage，保存 5 小时和 7 天两个窗口的利用率与重置时间，并线性外推窗口结束时的用量（projected）。窗口刚开始时外推分母太小，结果只作提前预警参考。

秘密

  • token 不出现在命令行参数、环境变量、事件或接口响应里；对外只出现 sha256 前 12 位指纹。
  • 脚本的 stdout/stderr 只写 <dataDir>/logs/scripts.log（0600），不经接口返回；写入前把当前 token 与形如 sk-ant-… 的串替换掉。脱敏只是兜底，脚本本身不应打印凭证。

keychain 分裂闸门（macOS）

如果 claude 在 keychain 里有这份凭证的条目（~/.claude 对应 Claude Code-credentials，其他目录对应 Claude Code-credentials-<目录 sha256 前 8 位>），它读的是 keychain 而不是我们刷新的文件。刷新会把 RT 转走、让 keychain 那份失效，所以此时拒绝刷新并告警 keychain_split。

LaunchDaemon 不一定看得到 login keychain，因此服务用一个哨兵条目（cred-keeper keychain-sentinel 创建）确认自己的可见性，并在 /healthz 的 keychainGate 报告 active 或 unavailable。只有 active 时闸门才生效；unavailable 期间照常刷新但跳过分裂检查，并持续告警——这是有意的 fail-open，否则开机后无人登录时 AT 会过期。

测试时绝不能创建不带后缀的 Claude Code-credentials 条目（在共享账号正在使用的机器上），否则所有使用 ~/.claude 的使用方都会立刻改读 keychain。
