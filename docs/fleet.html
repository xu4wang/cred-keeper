机队模式（跨机共享账号）

多台机器通过一个 Redis 共享账号：每台只刷新自己的号，bot 可以用任何机器的号。

单机模式下，一台机器上的 bot 只能用这台机器上登录的号。机队模式让多台机器通过一个 Redis 共享账号：每台机器仍只刷新自己的号，刷新后把凭证加密发布出去；其他机器把需要的号镜像到本地，bot 指向镜像即可。换号只改 bot 的一个配置项，与号在哪台机器刷新无关。

三件事

  • 发布（publish）：fleet.publish 里列出的本机号，每次刷新后、以及每 republishMin 分钟（默认 5），把凭证文件原样加密写进 ck:cred:<号>，并在 ck:events stream 上广播。
  • 镜像（mirrors）：别的机器负责刷新的号。收到广播立即拉取（另外每分钟兜底同步一次），只有严格更新的凭证才会替换本地副本（到期时间相同也不替换），替换在文件锁内完成，然后运行 onUpdated。
  • 查忙（busy）：副本进入所属号的刷新窗口（AT 剩不到 180 分钟）后，每分钟运行 busyCheck；退出码 75 表示本机有使用这个号的 bot 正在回复，写入带 TTL 的 ck:busy:<号>:<机器>。所属机器刷新前读取它，有人忙就推迟——规则与本机 preRefresh 完全相同，同样受 preRefreshMaxDeferMin / redMin 限制。

凭证原样传输

镜像副本与生产者的凭证文件逐字节一致，不改 schema；登录身份 oauthAccount 写进副本旁边的 .claude.json（该文件的其他字段保留）。所以 Claude Code 以后改凭证格式也不影响机队模式。

配置

"fleet": {
  "machine": "dev-prem",
  "redis": "redis://redis.example.lan:6379",
  "redisPasswordFile": "~/.cred-keeper/fleet-redis.pass",
  "keyFile": "~/.cred-keeper/fleet.key",
  "publish": { "default": "alpha", "acct1": "young" },
  "mirrors": [
    { "name": "tian",
      "credentialPath": "~/accounts/tian/claude/.credentials.json",
      "onUpdated": "~/.cred-keeper/hooks/fleet-botmux-mirror.sh",
      "busyCheck": "~/.cred-keeper/hooks/fleet-botmux-mirror.sh",
      "onStale":   "~/.cred-keeper/hooks/fleet-botmux-mirror.sh" }
  ]
}
字段默认含义
machine必填本机在机队里的名字（忙碌上报、事件来源）
redis必填redis://[:密码@]主机[:端口][/库]
redisPasswordFile—Redis 密码文件（0600），优先于 URL 里的密码
keyFile~/.cred-keeper/fleet.key机队密钥：32 字节 base64，每台机器同一份
publish{{}}本机账号 id → 机队统一号名
mirrors[].name必填要镜像的机队号名（不能和本机发布的重名）
mirrors[].credentialPath~/accounts/<name>/claude/.credentials.json副本位置；不能在 ~/.claude 里，不能与本机账号重复
mirrors[].onUpdated—副本更新后执行（环境变量同 onRefreshed，CK_EVENT=mirror_updated）
mirrors[].busyCheck—CK_EVENT=busy_check；75 = 忙
mirrors[].onStale—副本快过期仍未更新时执行一次（CK_EVENT=mirror_stale）
mirrors[].warnMin / errorMin45 / 20副本 AT 剩余少于此分钟数且未更新 → mirror_stale warn / mirror_expiring error
republishMin5未变化时也定期重写，Redis 重启清空后自动补满
busyTtlSec150忙碌上报的寿命；机器宕机后最多这么久就不再挡刷新

安全

  • 写进 Redis 的每个值（凭证和忙碌上报）都用机队密钥做 AES-256-GCM 加密，并把 key 名作为附加认证数据绑定——一个号的密文不能被挪去冒充另一个号。Redis 走明文 TCP 也看不到任何 token。
  • 密钥只生成一次：cred-keeper fleet-keygen <路径>（不会覆盖已有文件），把这个文件复制到每台机器（0600）。Redis 另设密码，只监听内网。
  • 镜像副本包含 RT（为了不改 schema）。生产者每次刷新都会轮换 RT，副本里的 RT 随即作废；新鲜度检查保证同步中断时提前告警。

故障语义

情况结果
Redis 不可达本机刷新、本机钩子完全不受影响；记 fleet_unreachable（每小时最多一次）。镜像暂停更新，恢复后自动追平
读不到忙碌状态不推迟刷新（不能因为 Redis 挂了就一直不刷）
Redis 重启、数据清空生产者 republishMin 内重新写满，无需人工
某台机器宕机它的忙碌上报在 busyTtlSec 后过期，不再挡别人刷新
密钥不一致 / 被篡改解密失败，副本不更新，记 mirror_unreadable error
旧值重放只接受到期时间严格更晚的凭证，旧值被忽略

在 botmux 上使用

  1. 使用方机器的 fleet.mirrors 加上要用的号，三个钩子都指向 examples/fleet-botmux-mirror.sh（它按 bots.json 自动找 bot，不需要维护名单）。
  2. 等副本出现：curl 127.0.0.1:8790/v1/fleet 里该镜像的 freshness 为 ok。
  3. 把 bot 的 credentialsSourceDir 改成副本的账号目录（如 ~/accounts/tian），对这个 bot 执行 botmux stop-bot / start-bot 和 botmux suspend --bot。
  4. 如果这个 bot 原来在别的号的钩子名单里，从名单里去掉。
  5. 验证：bot 冷启动后，它自己那份凭证的 AT 指纹应与该号一致。

部署 Redis 的参考配置

bind 127.0.0.1 <内网 IP>
protected-mode yes
requirepass <随机长密码>
save ""              # 只是缓存，不需要持久化
appendonly no
maxmemory 64mb
rename-command FLUSHALL ""
rename-command FLUSHDB ""
rename-command CONFIG ""
rename-command DEBUG ""

回滚

删掉 config.json 里的 fleet 段，热加载后立即回到单机模式；把 bot 的 credentialsSourceDir 改回原来的号即可。
