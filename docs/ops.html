运维与排障

事件与告警等级、常见问题的处理方法、维护注意事项。

事件与告警等级

所有事件都写进 state.db，可用 /v1/events 查询；达到 alert.minLevel 的才投递给告警脚本。同一问题在一个「事件期」内只告警一次，账号恢复健康后重新计。

refresh_retrywarn网络失败，下个周期重试

常见问题

账号进入 dead

RT 已失效（过期、被别的进程用掉、或被吊销）。只能在该账号的配置目录里人工 /login；登录后发布文件变新，服务会自动收编并恢复。RT 有固定到期时间（刷新不顺延），rt_expiring 会提前 rtWarnDays 天每天提醒。

账号进入 critical

看 /v1/accounts/<id> 的最近事件。若是 pending_unresolved，按提示用 cred-keeper pending <id> apply|discard --confirm <id> 处理；不确定时不要 discard，它可能持有唯一有效的 RT。

刷新后 bot 报认证失败

刷新立刻作废旧 AT。检查 hook_ok / hook_failed：钩子没成功 suspend，bot 就还拿着旧 AT。配置 preRefresh 可以避免在 bot 回复中途刷新。

镜像 freshness 不是 ok

  • missing：还没同步到。查 /v1/fleet 的 lastError（not published = 生产者还没发布；redis: … = 连不上 Redis）。
  • warn / error：副本快过期但没收到更新。先看生产者那台的账号状态（是否刷新失败、是否被推迟），再看两边能否连到 Redis。可以 cred-keeper fleet-sync 手动拉一次。

收不到用量预警

usage_high 是 warn 级别，默认 minLevel=error 时不投递。调低 minLevel，或者看用量看板。

维护注意

  • 强制刷新会吊销当前 AT：refresh --force 之后，所有使用方都必须换上新凭证。
  • 不要把凭证文件复制到别处「试一下」：那就是一次真刷新，会让原主机的 RT 失效。
  • 升级后看一眼 /healthz 与 /v1/accounts：指纹不变、状态 ok 即可。
  • 机队模式回滚：删掉 fleet 段即可回到单机；无需重启。
